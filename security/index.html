Security Architecture & Vulnerability Disclosure

Cryptographic specifications, data privacy boundaries, and our responsible disclosure process.

Threat Model Premise

The safest data is the data that is never collected. Kanri does not operate remote database servers, user tracking beacons, or telemetry pipelines. Your financial ledger resides exclusively inside your Android sandbox.

1. Cryptographic Standards

  • Database Storage: SQLCipher 256-bit AES-CBC with HMAC-SHA512 per-page integrity verification.
  • Master Key Encapsulation: Android Keystore System within device hardware Trusted Execution Environment (TEE) or StrongBox Keymaster.
  • Encrypted Backups: PBKDF2 with HMAC-SHA256 (65,536 iterations), 16-byte random salt, 12-byte random IV, and 256-bit AES-GCM with a 128-bit authentication tag.
  • Google Drive Sync: Scoped strictly to https://www.googleapis.com/auth/drive.file. Direct TLS connection to Google Drive API with zero proxy servers.

2. Permissions Scoping & Minimization

Kanri adheres to the principle of least privilege:

  • READ_SMS & RECEIVE_SMS: Processed in transient memory. Bank headers are matched; personal messages and OTP alerts are immediately dropped without logging.
  • NotificationListenerService: Filtered strictly to package names of supported UPI and banking apps.
  • No Contacts Permission: Contact names for Lend & Borrow are entered manually or selected via system intent without granting background contact address book access.
  • No Location Permission: Location is neither requested nor inferred.

3. Responsible Disclosure Policy

We take the security of Kanri very seriously. If you discover a security vulnerability or cryptographic flaw:

  1. Do not open a public GitHub issue.
  2. Submit a private vulnerability report via GitHub Security Advisories.
  3. Include reproduction steps, a proof-of-concept payload, and the affected version number.
  4. We will acknowledge receipt within 48 hours, coordinate a patch, and publish a security advisory giving you full credit.
